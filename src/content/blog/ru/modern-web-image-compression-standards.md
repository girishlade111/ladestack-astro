Изображения остаются главным источником веса страниц в современном интернете. Согласно статистике HTTP Archive, графика составляет свыше 45% от общего объема передаваемых данных для среднестатистического веб-ресурса. Для веб-разработчиков и продуктовых команд доставка визуально безупречных медиаресурсов при строгом соблюдении стандартов Core Web Vitals (в первую очередь Largest Contentful Paint — LCP) требует глубоко продуманной оптимизации.

Исторически сжатие графики всегда ассоциировалось с серверными микросервисами (такими как Sharp на Node.js или Cloudinary). Однако возможности современных браузерных API позволяют производить сжатие с потерями и без потерь непосредственно на клиентском устройстве до отправки, предпросмотра или сохранения файлов.

В этом руководстве мы разберем три фундаментальные стратегии клиентской оптимизации изображений, используемые в **LS Image** — утилите LadeStack для обработки графики в браузере, — и сопоставим их коэффициенты сжатия, совместимость и нагрузку на процессор.

## Стратегия 1: Повторное кодирование через HTML5 Canvas 2D

Самый доступный и универсальный способ сжатия на клиенте опирается на встроенный в браузер механизм 2D Canvas. После отрисовки изображения на элементе `<canvas>` разработчик может экспортировать растровый массив с помощью метода `HTMLCanvasElement.toBlob()`.

```typescript
/**
 * Сжимает изображение с использованием стандартного HTML5 Canvas API
 */
export async function compressViaCanvas(
  file: File,
  quality: number = 0.8,
  targetFormat: 'image/jpeg' | 'image/webp' = 'image/webp'
): Promise<Blob> {
  const bitmap = await createImageBitmap(file);
  const canvas = document.createElement('canvas');
  canvas.width = bitmap.width;
  canvas.height = bitmap.height;

  const ctx = canvas.getContext('2d', { alpha: targetFormat === 'image/webp' });
  if (!ctx) {
    throw new Error('Canvas 2D context not supported');
  }

  ctx.drawImage(bitmap, 0, 0);

  return new Promise((resolve, reject) => {
    canvas.toBlob(
      (blob) => {
        if (blob) resolve(blob);
        else reject(new Error('Canvas toBlob serialization failed'));
      },
      targetFormat,
      quality
    );
  });
}
```

### Преимущества повторного кодирования через Canvas:
- **Отсутствие внешних зависимостей:** Использует штатные графические библиотеки браузера без необходимости загружать сторонний JavaScript-код.
- **Аппаратное ускорение:** Браузер делегирует растеризацию холста и обработку пикселей графическому ускорителю (GPU).
- **Кроссбраузерность:** 100% поддержка на всех актуальных десктопных и мобильных платформах.

## Стратегия 2: Кодирование в формат WebP

Разработанный Google формат WebP стал общепринятым стандартом для веба. При идентичных показателях структурного сходства (SSIM) он обеспечивает уменьшение размера файла на 25–34% по сравнению с классическим JPEG.

В клиентском коде кодирование WebP доступно напрямую через вызов `canvas.toBlob(callback, 'image/webp', quality)`. Движки Blink, Gecko и WebKit (начиная с Safari 14) содержат оптимизированные нативные кодеры libwebp.

```typescript
// Пошаговое снижение качества для достижения заданного лимита байтов
export async function compressToByteBudget(
  file: File,
  maxBytes: number = 200 * 1024 // Цель: не более 200 КБ
): Promise<Blob> {
  let quality = 0.85;
  let compressedBlob = await compressViaCanvas(file, quality, 'image/webp');

  while (compressedBlob.size > maxBytes && quality > 0.4) {
    quality -= 0.1;
    compressedBlob = await compressViaCanvas(file, quality, 'image/webp');
  }

  return compressedBlob;
}
```

## Стратегия 3: Сжатие следующего поколения AVIF

Формат AVIF (AV1 Image File Format), основанный на видеокодеке AV1 консорциума Alliance for Open Media (AOMedia), находится на острие технологий компрессии. Он превосходит WebP, позволяя получать файлы на **50% меньше JPEG** и на **20% компактнее WebP** при великолепном сохранении микроконтраста, плавных градиентов и четких текстовых контуров.

В то время как нативная поддержка создания AVIF через `canvas.toBlob('image/avif')` постепенно внедряется в браузеры, модули WebAssembly на базе `libavif` позволяют генерировать файлы AVIF в любой современной среде без задержек.

## Практический бенчмарк: степень сжатия и длительность кодирования

Для наглядного сопоставления характеристик мы провели тесты на несжатой фотографии с зеркальной камеры объемом 4,2 МБ (4032 × 3024 пикселей, 24-битный sRGB) при эквивалентном визуальном качестве (SSIM ~ 0,94):

| Формат и метод | Размер результата | Уменьшение | Время (M2 Mac) | Время (смартфон сред. уровня) |
|:---|:---:|:---:|:---:|:---:|
| **Исходный JPEG** | 4 200 КБ | 0% (базовый) | — | — |
| **Canvas JPEG (q=0.82)** | 1 120 КБ | -73.3% | 42 мс | 115 мс |
| **Canvas WebP (q=0.80)** | 780 КБ | -81.4% | 68 мс | 185 мс |
| **WASM AVIF (Speed=6, q=65)** | **460 КБ** | **-89.0%** | 380 мс | 1 240 мс |

### Выводы для архитектуры:
1. **Для мгновенной пакетной обработки:** Оптимальным выбором является WebP через нативный Canvas. Он гарантирует сжатие свыше 80% за доли секунды (<100 мс).
2. **Для максимальной экономии трафика:** AVIF незаменим в условиях медленного соединения. Для предотвращения микрофризов интерфейса процесс кодирования рекомендуется выносить в фоновые Web Workers.

## Внедрение оптимизации на стороне клиента

Сжатие графики перед загрузкой в облачные хранилища Amazon S3, Cloudflare R2 или Firebase обеспечивает три ключевых преимущества:
- **Снижение расходов на хранилище:** Хранение файлов WebP размером 700 КБ вместо исходников на 5 МБ экономит более 80% бюджета.
- **Ускорение отправки данных:** Уменьшение объема передаваемых пакетов в мобильных сетях сокращает процент отказов пользователей при заполнении веб-форм.
- **Сокращение исходящего трафика (Egress):** Легкие изображения ускоряют рендеринг LCP и улучшают позиции в поисковых системах.
