## 1. Введение: Зачем микросервисной архитектуре необходим API Gateway

В распределенной микросервисной архитектуре прямое взаимодействие клиентских приложений (веб-интерфейсов, мобильных клиентов, сторонних интеграций) с десятками изолированных внутренних сервисов является грубым антипаттерном.

Прямая схема взаимодействия приводит к критическим архитектурным проблемам:
- **Жесткая связанность клиентов с внутренней структурой:** Любое разделение сервисов, переименование или изменение маршрутов требует принудительного обновления всех клиентских приложений.
- **Расширение периметра атак:** Каждый микросервис вынужден иметь публичный сетевой адрес, что приводит к фрагментации политик безопасности, CORS и TLS-сертификатов.
- **Дублирование сквозной функциональности:** Каждая команда заново изобретает валидацию JWT, ограничение частоты запросов и логирование, что порождает неконсистентность и уязвимости.
- **Высокая сетевая задержка:** Мобильное приложение вынуждено выполнять десятки последовательных HTTP-запросов для загрузки одного экрана.

```
Сравнение архитектур: Прямой доступ против API Gateway
======================================================
Прямой доступ (Антипаттерн):
[Мобильный клиент] ──┬──► [Auth Service :8081]
                     ├──► [Order Service :8082]
                     ├──► [Payment Service :8083]
                     └──► [Inventory Service :8084]

Паттерн API Gateway (Рекомендованный подход):
                     ┌────────────────────────────────────────────────────────┐
                     │                 API Gateway (:443)                     │
                     │  - Терминация SSL & Политики CORS                      │
                     │  - Проверка подписей JWT & Проброс заголовков          │
                     │  - Распределенный Rate Limiting в Redis (Token Bucket) │
                     │  - Маршрутизация, таймауты и Circuit Breakers          │
                     └──────────────────────────┬─────────────────────────────┘
                                                │ Защищенная сеть VPC (mTLS)
                           ┌────────────────────┼────────────────────┐
                           ▼                    ▼                    ▼
                   [Auth Service]        [Order Service]      [Payment Service]
```

API Gateway выступает единой точкой входа (обратным прокси) на границе системы, консолидируя управление сквозными аспектами.

## 2. Ключевые компоненты и функциональные уровни шлюза

Production-ready API Gateway реализует следующие обязательные уровни обработки трафика:

| Уровень функциональности | Обязанности шлюза | Механизм и протоколы |
| :--- | :--- | :--- |
| **Обратный прокси и маршрутизация** | Преобразование внешних URI в адреса внутренних микросервисов | Сопоставление префиксов, регулярные выражения, канареечные веса |
| **Аутентификация на границе сети** | Криптографическая валидация токенов, обогащение контекста | Валидация JWT RS256/EdDSA, кэширование JWKS, mTLS |
| **Управление трафиком и Rate Limiting** | Защита от DoS-атак и соблюдение квот арендаторов | Распределенный алгоритм Token Bucket на базе Redis |
| **Отказоустойчивость (Resilience)** | Предотвращение каскадных аварий при сбоях | Таймауты, экспоненциальный backoff при повторах, Circuit Breakers |
| **Распределенная трассировка** | Сквозной мониторинг транзакций через цепочки вызовов | Стандарт W3C TraceContext (`traceparent`), OpenTelemetry |
| **Трансляция протоколов** | Разделение внешних и внутренних форматов взаимодействия | Преобразование внешнего HTTP/1.1・HTTP/2 во внутренний gRPC/Protobuf |

## 3. Аутентификация, авторизация и эшелонированная оборона (Defense in Depth)

### Фундаментальный принцип: Аутентификация на шлюзе не отменяет авторизацию в сервисах
Распространенным заблуждением является мнение, что «если запрос успешно прошел проверку токена на шлюзе, внутренний сервис может слепо доверять входящим вызовам».

При компрометации шлюза или прямом доступе из внутренней подсети сервисы остаются беззащитными. Принцип **Defense in Depth** требует:

```
Схема сквозной эшелонированной аутентификации
--------------------------------------------
[Клиент]
   │ 1. Authorization: Bearer <JWT>
   ▼
[API Gateway]
   │ 2. Проверяет цифровую подпись JWT с помощью локально закэшированного JWKS
   │ 3. Проверяет срок действия (exp) и издателя (iss); отклоняет невалидные запросы (401)
   │ 4. Инкапсулирует проверенные клеймы в доверенные внутренние заголовки:
   │    - X-User-Id: 98412
   │    - X-User-Roles: billing_admin,user
   │    - X-Tenant-Id: tenant_corp_a
   ▼
[Внутренний микросервис]
   │ 5. Проверяет подлинность соединения шлюза по mTLS
   │ 6. Выполняет собственную бизнес-авторизацию на основе X-User-Roles
   │ 7. Исполняет бизнес-логику
```

## 4. Распределенный Rate Limiting: Алгоритм Token Bucket в Redis

Локальное ограничение частоты запросов в оперативной памяти процесса перестает работать при горизонтальном масштабировании инстансов шлюза. При 10 репликах лимит неконтролируемо возрастает в 10 раз.

Использование атомарных Lua-скриптов в Redis обеспечивает микросекундную точность распределенного ограничения:

```lua
-- Redis Token Bucket Rate Limiting (Atomic Lua Script)
-- KEYS[1]: Ключ лимита (например: ratelimit:tenant_123:orders)
-- ARGV[1]: Максимальная емкость ведра (Max Burst)
-- ARGV[2]: Скорость пополнения токенов (токенов в секунду)
-- ARGV[3]: Текущее время Unix (в секундах)
-- ARGV[4]: Количество запрашиваемых токенов (обычно 1)

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local fill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local data = redis.call('HMGET', key, 'tokens', 'last_updated')
local tokens = tonumber(data[1])
local last_updated = tonumber(data[2])

if not tokens then
    tokens = capacity
    last_updated = now
else
    local elapsed = math.max(0, now - last_updated)
    tokens = math.min(capacity, tokens + (elapsed * fill_rate))
    last_updated = now
end

if tokens >= requested then
    tokens = tokens - requested
    redis.call('HMSET', key, 'tokens', tokens, 'last_updated', last_updated)
    redis.call('EXPIRE', key, math.ceil(capacity / fill_rate) * 2)
    return {1, math.floor(tokens)} -- 1 = Разрешено
else
    redis.call('HMSET', key, 'tokens', tokens, 'last_updated', last_updated)
    return {0, 0} -- 0 = Превышен лимит (429 Too Many Requests)
end
```

## 5. Паттерны отказоустойчивости: Таймауты, ретраи и Circuit Breakers

1. **Таймауты:** Таймаут ожидания ответа на шлюзе должен быть строго меньше таймаута вызываемого сервиса во избежание зависания пулов соединений.
2. **Идемпотентные повторы:** Автоматические повторы (retries) разрешены исключительно для безопасных идемпотентных методов (GET, PUT, DELETE). Повтор POST-запросов оплаты приведет к двойному списанию средств.
3. **Circuit Breakers (Автоматические предохранители):** Если сервис возвращает более 50% ошибок, цепь переходит в состояние OPEN, мгновенно возвращая дефолтный ответ и защищая сервис от окончательного коллапса.

## 6. Сравнение технологий: Envoy vs NGINX vs Kong

| Критерий | Envoy Proxy | NGINX (Open Source / Plus) | Kong Gateway |
| :--- | :--- | :--- | :--- |
| **Язык разработки** | C++ (минимальная задержка и управление памятью) | C (проверенная временем архитектура) | Lua / OpenResty (поверх NGINX) |
| **Обновление конфигурации** | Динамическое через xDS API без перезагрузок | Статическое с перезагрузкой воркеров | Динамическое через REST API и decK |
| **Сетевые протоколы** | HTTP/1.1, HTTP/2, HTTP/3, gRPC | HTTP/1.1, HTTP/2, gRPC | HTTP/1.1, HTTP/2, gRPC |
| **Расширяемость** | Фильтры WebAssembly (Wasm) и C++ | Модули на C, njs (JavaScript) | Плагины на Lua и Wasm |
| **Основной сценарий** | Cloud Native, Kubernetes Ingress, Service Mesh | Статическая раздача, классический прокси | Корпоративное управление API |

## 7. API Gateway против Service Mesh

- **API Gateway (North-South трафик):** Контролирует трафик из внешнего интернета в периметр инфраструктуры (авторизация клиентов, биллинг, квоты, версионирование).
- **Service Mesh (East-West трафик):** Управляет коммуникацией между микросервисами внутри кластера (Istio, Linkerd), обеспечивая сквозное mTLS шифрование и канареечные переключения.
