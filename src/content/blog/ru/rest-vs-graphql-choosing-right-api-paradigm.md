Дискуссия о выборе между REST (Representational State Transfer) и GraphQL давно вышла за рамки идеологических споров и превратилась в практическую инженерную оценку характеристик нагрузки, требований к кэшированию и сложности инфраструктуры. Восприятие GraphQL как безусловной замены REST без учета специфики систем приводит к архитектурным просчетам.

В этом руководстве мы сопоставим две парадигмы — ресурсно-ориентированный REST и графо-ориентированный GraphQL, разберем решение проблемы N+1 с помощью DataLoader, оценим возможности кэширования на CDN и сформируем матрицу выбора для высоконагруженных систем.

---

## Архитектурные парадигмы: ресурсы против графа

```
REST (ориентация на ресурсы):
GET /api/v1/users/42          ──► [Данные пользователя]
GET /api/v1/users/42/orders   ──► [Список заказов]
GET /api/v1/products/808      ──► [Карточка товара]
(Несколько последовательных запросов или перегруженные составные эндпоинты)

GRAPHQL (ориентация на граф):
POST /graphql
{
  user(id: "42") {
    name
    orders { id total product { title price } }
  }
}                             ──► [Точный набор полей в рамках одного запроса]
```

### Модель REST
Система моделируется как набор независимых ресурсов, идентифицируемых стабильными URI. Управление состоянием осуществляется стандартными HTTP-методами (`GET`, `POST`, `PUT`, `DELETE`).
- **Преимущества:** Полная нативная интеграция с протоколом HTTP, зрелая экосистема, предсказуемые URL и простая интеграция с промежуточным кэшированием (CDN).
- **Недостатки:** Риск избыточной передачи данных (**Over-fetching**) и необходимость множественных сетевых запросов для сбора составных экранов (**Under-fetching**).

### Модель GraphQL
Использует строго типизированную схему и декларативный язык запросов, позволяя клиенту запрашивать ровно те поля и связи, которые необходимы для отрисовки интерфейса.
- **Преимущества:** Исключение избыточных данных, сбор реляционных данных в одном запросе, контрактная типизация.
- **Недостатки:** Потеря простого HTTP-кэширования, сложность защиты от перегружающих вложенных запросов и системная проблема N+1.

## Кэширование: HTTP Edge против нормализованного хранилища клиента

При высоких нагрузках на чтение именно эффективность кэша определяет жизнеспособность архитектуры.

### REST: Бесплатное кэширование на CDN
Запросы `GET` в REST обладают уникальными URI, благодаря чему пограничные прокси-серверы (Cloudflare, AWS CloudFront) мгновенно кэшируют ответы:

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=3600, stale-while-revalidate=60
ETag: W/"33a64df551425fcc55e4d42a148795d9f25f89d4"
Content-Type: application/json
```

Попадание в кэш на ближайшем узле PoP обслуживается за считанные миллисекунды без обращения к базам данных и серверам приложения.

### GraphQL: Специфика POST-запросов
Поскольку запросы GraphQL отправляются через HTTP `POST` на единый эндпоинт `/graphql`, стандартные прокси-серверы не могут кэшировать ответы на уровне URL. Клиенты вынуждены поддерживать сложные клиентские кэши (Apollo Client) или внедрять механизм APQ (Automatic Persisted Queries).

## Решение проблемы N+1 с помощью DataLoader

В наивной реализации резолверов GraphQL запрос списка сущностей со связанными данными провоцирует лавину запросов к базе данных — известную проблему **N+1**. Стандартным архитектурным решением является пакетирование (batching) через **DataLoader**:

```typescript
import DataLoader from 'dataloader';
import { db } from './database';

interface Order {
  id: string;
  userId: string;
  total: number;
}

export function createOrderLoader() {
  return new DataLoader<string, Order[]>(async (userIds: readonly string[]) => {
    // Единый пакетный SQL-запрос: SELECT * FROM orders WHERE user_id = ANY($1)
    const orders = await db.query(
      `SELECT * FROM orders WHERE user_id = ANY($1)`,
      [userIds]
    );

    const orderMap = new Map<string, Order[]>();
    for (const userId of userIds) {
      orderMap.set(userId, []);
    }
    for (const order of orders) {
      orderMap.get(order.userId)?.push(order);
    }

    return userIds.map((id) => orderMap.get(id) || []);
  });
}
```

## Матрица выбора для продакшена

### Выбирайте REST, если:
1. **Публичный API для внешних интеграций:** Сторонние разработчики используют стандартные HTTP-клиенты без привязки к библиотекам GraphQL.
2. **Преобладание чтения с критической важностью CDN-кэширования:** Медиапорталы, каталоги товаров в электронной коммерции.
3. **Передача крупных бинарных файлов:** Загрузка и потоковое вещание видео, PDF или графических материалов.

### Выбирайте GraphQL, если:
1. **Множество разнородных клиентских платформ (Mobile / Web / Wearables):** Каждому клиенту требуется строго оптимизированный объем данных.
2. **Сложные аналитические панели и агрегаторы:** Интерфейсы, объединяющие десятки микросервисов в едином представлении.
3. **Высокая скорость продуктовых итераций фронтенда:** Клиентские команды могут изменять структуру запросов без ожидания доработок на бэкенде.
